# 模型生成参数配置指南

## 概述

LLM 生成参数控制模型的输出行为。合理配置这些参数可以在**质量、速度、成本**之间取得平衡。

## 核心参数

### 1. MAX_TOKENS

**作用**: 控制单次生成的最大 token 数量

**影响**:
- ✅ 更大的值 → 更完整的输出
- ⚠️ 更大的值 → 更高的成本和延迟
- ❌ 太小 → 内容被截断

**推荐值**:
| 场景 | 推荐值 | 说明 |
|------|--------|------|
| 简单测试用例（3-5个） | 1024-1536 | 基本够用 |
| 标准测试用例（5-8个） | 2048 | 平衡选择 ✅ |
| 详细测试用例（8-12个） | 3072 | 边界测试 |
| 大批量生成 | 4096 | 最大限制 |

**示例**:
```env
# 开发环境 - 快速迭代
MAX_TOKENS=1536

# 生产环境 - 完整输出
MAX_TOKENS=2048

# 边界测试 - 详细场景
EDGE_CASE_MAX_TOKENS=3072
```

---

### 2. TEMPERATURE

**作用**: 控制输出的随机性/创造性

**值域**: 0.0 - 1.0

**影响**:
- **0.0-0.3**: 非常确定性，输出一致
  - ✅ 适合：需要稳定输出的场景
  - ❌ 缺点：缺乏创造性，可能重复

- **0.4-0.7**: 平衡模式（推荐）
  - ✅ 适合：大多数测试用例生成
  - ✅ 既有一致性又有适度变化

- **0.8-1.0**: 高创造性
  - ✅ 适合：边界测试、探索性测试
  - ⚠️ 可能产生不够准确的输出

**推荐值**:
```env
# 标准测试用例 - 稳定输出
TEMPERATURE=0.7

# 边界测试 - 创造性场景
EDGE_CASE_TEMPERATURE=0.8

# 回归测试生成 - 最大一致性
TEMPERATURE=0.3
```

**效果对比**:

| Temperature | 输出特点 | 示例 |
|-------------|---------|------|
| 0.3 | 每次生成几乎相同的测试用例 | "验证用户登录-正常流程" |
| 0.7 | 测试用例有变化但保持合理性 | "验证用户登录功能的正常场景" |
| 0.9 | 产生多样化的测试角度 | "探索用户认证系统的边界行为" |

---

### 3. TOP_P

**作用**: 控制采样的多样性（核采样）

**值域**: 0.0 - 1.0

**原理**:
- 从累积概率达到 top_p 的 token 中采样
- top_p=1.0 表示考虑所有 token
- top_p=0.9 表示只考虑累积概率前 90% 的 token

**影响**:
- **0.5-0.7**: 保守采样
  - ✅ 输出更可预测
  - ❌ 可能缺乏多样性

- **0.8-0.95**: 平衡采样（推荐）
  - ✅ 既保证质量又有变化
  - ✅ 适合大多数场景

- **0.95-1.0**: 广泛采样
  - ✅ 最大多样性
  - ⚠️ 可能产生不太相关的内容

**推荐值**:
```env
# 标准配置
TOP_P=0.9

# 严格场景（如安全测试）
TOP_P=0.8

# 创新场景（如探索性测试）
TOP_P=0.95
```

## 参数组合建议

### 场景 1: 功能测试用例（标准）

**目标**: 稳定、全面、可重复

```env
MAX_TOKENS=2048
TEMPERATURE=0.7
TOP_P=0.9
```

**效果**:
- ✅ 生成 5-8 个标准功能测试用例
- ✅ 输出稳定，每次运行结果相似
- ✅ 成本适中

---

### 场景 2: 边界/异常测试用例

**目标**: 详细、创造性、全面覆盖

```env
EDGE_CASE_MAX_TOKENS=3072
EDGE_CASE_TEMPERATURE=0.8
TOP_P=0.9
```

**效果**:
- ✅ 生成 8-12 个详细的边界测试用例
- ✅ 更高的创造性发现边缘场景
- ✅ 避免内容被截断

---

### 场景 3: 回归测试生成（严格）

**目标**: 确定性、可重复

```env
MAX_TOKENS=1536
TEMPERATURE=0.3
TOP_P=0.8
```

**效果**:
- ✅ 每次生成几乎相同的测试用例
- ✅ 适合 CI/CD 中的自动化测试
- ✅ 最低成本

---

### 场景 4: 探索性测试（创新）

**目标**: 发现新的测试角度

```env
MAX_TOKENS=3072
TEMPERATURE=0.9
TOP_P=0.95
```

**效果**:
- ✅ 产生非常规的测试思路
- ⚠️ 需要人工审核质量
- ⚠️ 成本较高

## 成本影响

### Token 成本估算

假设 API 定价（以通义千问为例）：
- 输入: ¥0.008 / 1K tokens
- 输出: ¥0.008 / 1K tokens

| 配置 | 单次成本 | 1000次成本 |
|------|---------|-----------|
| MAX_TOKENS=1024 | ¥0.008-0.016 | ¥8-16 |
| MAX_TOKENS=2048 | ¥0.016-0.032 | ¥16-32 |
| MAX_TOKENS=3072 | ¥0.024-0.048 | ¥24-48 |
| MAX_TOKENS=4096 | ¥0.032-0.064 | ¥32-64 |

**优化建议**:
- 开发测试用较小的 MAX_TOKENS
- 生产环境按需调整
- 批量生成时考虑成本

## 调试和优化

### 1. 监控日志

启用详细日志查看 token 使用：

```python
logger.debug(f"Edge case LLM response length: {len(response)} chars")
logger.warning(f"Parsed {len(testcases)} test cases from truncated response (repaired)")
```

### 2. 常见问题

**问题 1: 内容经常被截断**
```
WARNING: Parsed 5 test cases from truncated response (repaired)
```

**解决**:
```env
# 增加 MAX_TOKENS
MAX_TOKENS=3072  # 从 2048 增加
```

---

**问题 2: 生成的测试用例太相似**
```
生成的10个用例中有5个重复
```

**解决**:
```env
# 提高随机性
TEMPERATURE=0.8  # 从 0.7 增加
TOP_P=0.95       # 从 0.9 增加
```

---

**问题 3: 生成的用例质量不稳定**
```
有时生成很好的用例，有时很差
```

**解决**:
```env
# 降低随机性
TEMPERATURE=0.5  # 从 0.7 降低
TOP_P=0.85       # 从 0.9 降低
```

---

**问题 4: 成本太高**
```
每月 API 调用成本超预算
```

**解决**:
```env
# 减少 token 使用
MAX_TOKENS=1536           # 从 2048 降低
EDGE_CASE_MAX_TOKENS=2048 # 从 3072 降低

# 或在 prompt 中要求更简洁的输出
```

## 总结

### 关键要点

1. ✅ **始终从环境变量读取配置** - 便于调整和部署
2. ✅ **为不同场景使用不同配置** - 边界测试 vs 标准测试
3. ✅ **监控和优化** - 根据日志调整参数
4. ✅ **平衡质量和成本** - 不是越大越好

### 推荐配置

**开发环境**:
```env
MAX_TOKENS=1536
TEMPERATURE=0.7
TOP_P=0.9
EDGE_CASE_MAX_TOKENS=2048
EDGE_CASE_TEMPERATURE=0.8
```

**生产环境**:
```env

TEMPERATURE=0.7
TOP_P=0.9
```
