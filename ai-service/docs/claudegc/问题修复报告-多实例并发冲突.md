# Qdrant多实例并发访问冲突修复报告

**问题编号**: #002
**修复日期**: 2025-12-05
**影响范围**: Feedback API, 向量数据库存储
**严重程度**: P1 (高)

## 一、问题概述

在修复了HuggingFace离线模式冲突问题后,用户在调试模式下重启服务(端口8080)时,再次遇到feedback接口无法存储到向量数据库的问题。同时伴随日志格式错误。

## 三、根本原因分析

### 3.1 Qdrant多实例冲突

**问题根源**:
- Qdrant的内存模式(memory mode with persistence)不支持多个客户端同时访问同一个存储文件夹
- 用户在端口8000已有服务运行时,又在端口8080启动了新服务
- 两个服务实例都尝试初始化Qdrant并访问同一个存储路径,导致后启动的实例无法获取锁

**技术细节**:
```
时间线:
19:04:53 - 端口8000服务启动,成功初始化Qdrant
19:08:54 - 端口8080服务启动,尝试访问相同的Qdrant存储
19:08:54 - ERROR: Storage folder is already accessed by another instance
19:08:54 - 端口8080服务进入降级模式(degraded mode)
```

**为什么无法自动恢复**:
- Qdrant客户端在初始化时失败后,不会自动重试
- 即使端口8000的服务后来被杀掉,端口8080的服务已经处于降级模式,不会重新尝试连接
- 必须重启服务才能重新初始化Qdrant

### 3.2 日志格式配置错误

**问题文件**: `logging_config.yaml`

**错误配置**(第13行):
```yaml
access:
  format: '%(asctime)s - %(levelname)s - %(client_addr)s - "%(request_line)s" %(status_code)s'
  #                                      ^^^^^^^^^^^^^^^^
  #                                      这个字段不存在!
```

**原因**:
- `%(client_addr)s`, `%(request_line)s`, `%(status_code)s` 是Uvicorn特有的字段
- 但它们并不作为标准的日志记录属性存在
- Uvicorn在访问日志中使用自己的格式化逻辑,但当使用标准的Python logging格式化时会失败

## 四、解决方案

### 4.1 修复Qdrant多实例冲突

#### 方案一:确保单实例运行(已采用)

**实施步骤**:

1. **停止所有运行中的服务**:
```bash
lsof -ti:8000,8080 | xargs kill -9 2>/dev/null
sleep 2
```

2. **启动单个干净的服务实例**:
```bash
source .venv/bin/activate && \
uvicorn main:app --host 0.0.0.0 --port 8080 --log-config logging_config.yaml
```

3. **验证Qdrant正常初始化**:
```
2025-12-05 19:13:22 - data.qdrant_client - INFO - ✅ Qdrant client initialized successfully
```

#### 方案二:使用Qdrant Server模式(长期方案)

如果需要支持多实例部署,应改用Qdrant Server模式:

**配置更改** (`config.py`):
```python
# 从内存模式改为服务器模式
QDRANT_MODE: str = 'server'  # 原来是 'memory'
QDRANT_HOST: str = 'localhost'
QDRANT_PORT: int = 6333
```

**启动Qdrant Server**:
```bash
# 使用Docker
docker run -p 6333:6333 -p 6334:6334 \
    -v $(pwd)/data/qdrant_storage:/qdrant/storage \
    qdrant/qdrant

# 或使用本地安装
qdrant --storage-path ./data/qdrant_storage
```

**优点**:
- 支持多个客户端并发访问
- 更好的性能和稳定性
- 适合生产环境

**缺点**:
- 需要额外的服务进程
- 增加部署复杂度

### 4.2 修复日志格式错误

**修改文件**: `logging_config.yaml`

**修改前**(第12-14行):
```yaml
access:
  format: '%(asctime)s - %(levelname)s - %(client_addr)s - "%(request_line)s" %(status_code)s'
  datefmt: '%Y-%m-%d %H:%M:%S'
```

**修改后**(第12-14行):
```yaml
access:
  format: '%(asctime)s - %(levelname)s - %(message)s'
  datefmt: '%Y-%m-%d %H:%M:%S'
```

**说明**:
- 移除了不存在的自定义字段
- 使用标准的 `%(message)s` 字段
- Uvicorn会自动在message中包含访问日志信息

## 七、技术总结

### 7.1 关键经验教训

1. **Qdrant内存模式的限制**:
   - 内存模式不支持并发访问
   - 适合开发和单机部署
   - 生产环境应使用Server模式

2. **服务实例管理**:
   - 在启动新实例前应检查并清理旧实例
   - 使用进程管理工具(如systemd, supervisor)确保单实例运行
   - 调试时注意端口和资源冲突

3. **日志配置的标准化**:
   - 避免使用框架特定的非标准字段
   - 使用标准的logging模块字段名
   - 测试日志配置以确保兼容性

4. **降级模式的陷阱**:
   - 降级模式一旦触发不会自动恢复
   - 需要重启服务才能重新初始化资源
   - 应该增加健康检查和自动重启机制

### 7.2 最佳实践建议

#### 开发环境

```bash
# 1. 启动服务前清理旧进程
lsof -ti:8080 | xargs kill -9 2>/dev/null

# 2. 使用明确的端口
uvicorn main:app --host 0.0.0.0 --port 8080 --reload

# 3. 监控日志
tail -f logs/ai-service.log
```

#### 生产环境

```bash
# 1. 使用Qdrant Server模式
docker-compose up -d qdrant

# 2. 使用进程管理器
systemctl start synapsetest-ai

# 3. 配置健康检查
curl http://localhost:8080/health

# 4. 配置日志轮转
logrotate /etc/logrotate.d/synapsetest-ai
```
